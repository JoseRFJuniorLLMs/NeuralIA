# SPEC-0006 — Security and Privacy

**Status:** Normative

Defaults:
- HTTP(S) only;
- no embedded URL credentials;
- local filesystem paths are rejected and MUST NOT become remote search queries;
- no site JavaScript in Reader;
- bounded Reader body, redirects, deadline and concurrency;
- every Reader redirect is validated before the next request;
- public Reader DNS resolution rejects loopback/private/link-local/reserved IP destinations;
- operating-system TLS certificate verification;
- no NeuralIA cloud account;
- bounded local history only;
- no default remote telemetry.

Remote HTML is untrusted input. Reader output is generated from escaped text blocks, not copied raw markup, and is served with a Content Security Policy that forbids scripts, connections, frames and objects.

Full Web mode inherits the patch level and sandbox model of the installed system WebView runtime. New sensitive WebView permission requests are denied by default. Top-level navigation on remote web surfaces is restricted to HTTP(S) plus `view-source:`; the `neuralia:` navigation scheme is rejected there and survives only for internal Reader links.

Remote WebView surfaces have a bounded WebView2 message channel, not ambient native authority. Each JSON message is limited to 8 KiB, belongs to a closed action schema, and must carry a per-WebView capability token generated by the operating-system CSPRNG and compared in constant time. `chrome.webview.postMessage` and `JSON.stringify` are captured at document-created time; the capability is never placed in a navigation URL, so the Chromium Navigation API cannot observe it as `destination.url`. Unknown actions, unexpected fields, wrong types, invalid columns and local-network split targets are rejected. The floating omnibox remains a native Win32 control: a page may request that it open, but can neither read nor submit what is typed into it.

The optional Gmail monitor is background network activity the user is entitled to know about. When a Google session already exists in the WebView2 profile, a hidden WebView keeps `mail.google.com` loaded so new mail can be announced natively. It consumes the session cookies that are already in the profile to tell whether a session exists; it never asks for a password, never copies those cookies out of the profile, and sends nothing to NeuralIA or to any third party. It only runs while such a session exists, and `NEURALIA_NO_GMAIL=1` disables it.

Local history writes MUST occur off the UI thread and retention MUST be bounded. The user MUST have a local clear-history action.

The repository MUST NOT contain secrets, cookies, tokens, private certificates, or user history.

## Persistence chokepoint (infra-privacy-guard, 2.4)

**Status:** Partial — phase 0 (the enumeration below and the gates that pin it); the private mode itself is not reachable in the product until `private-mode-core`.

Every store under `<data_dir>` has one `StoreKind` (`neural_core::json_store`): `Setting` changes only by an explicit choice in a menu or setting; `Explicit` is content the user asked to keep; `Automatic` is a side effect of use. A store opens only with a `StoreGrant`, and the only source of grants in the product is the `StoreRegistry` minted once in `App::new` and owned by the `PrivacyGuard` (`crates/neural-app/src/privacy.rs`), which never lends the registry out: features ask `guard.store(spec)`. The guard also routes the three `Automatic` writers that are side effects of browsing — the history (`record`), the semantic memory (`capture`, `save_session`, `rebuild_memory`) and the tab session (`save_tabs`, `save_tabs_due`) — and, while the shared mode says `Private`, those writes are no-ops and the guard's reads (`recent_history`, `query_memory`, `restore_tabs`) write nothing: `restore_tabs` leaves a damaged `tabs.json` where it is instead of moving it to `tabs.json.bak` (`SessionStore::peek`), and a history read in a folder no writer has touched does not create `history.jsonl.lock`. The gate `private_guard_turns_automatic_stores_into_noops` drives a whole session through the guard — those reads, those writes, the debounced tab save with a current and a stale token, and `memory:rebuild` — in `Private` over a data dir a `Normal` session already filled (with a damaged `tabs.json`), snapshotting before the guard is built, and requires it byte-identical; `Private` is reachable only through a `cfg(test)` constructor. Exceptions, in any mode: building the guard opens the tab writer lock (`tabs.lock`, empty) and the empty `memory/` directories, so a data dir no session ever touched gains the empty `tabs.lock` (same gate); "Apagar histórico" (`clear_history`, `clear_memory`, `forget_tabs`) writes tombstones and `tabs.cleared` because it is privacy; a memory query over a 2.0.x index migrates it (`query_migrates_a_2_0_index_before_answering`) and opening the index restores the backup a crashed rebuild left behind (`interrupted_swap_restores_fixed_backup_on_next_open`) — derived data, no new content.

### Phase 0 — every writer under the data dir

The gate `no_raw_data_dir_write_outside_a_grant` (`windows_app/tests.rs`) counts `fs::write`, `File::create`, `OpenOptions::new`, `File::options`, `fs::rename`, `fs::copy` and `Connection::open*` (SQLite) in every shipped `.rs` file under `crates/neural-app/src` and `crates/neural-core/src` (a directory walk; tests, comments and string literals stripped), fails on a `use` that brings one of those writes in under a name it does not count (a bare `use std::fs::write`, or a renamed `File`, `OpenOptions`, `Connection` or `std::fs` item), and fails on any occurrence outside `json_store.rs` that is not in its allowlist — one row per file, one reason per row, the same rows as this table. A file that starts writing raw turns the gate red until this table and the allowlist say why.

The gate `history_memory_and_tabs_are_written_only_through_the_privacy_guard` walks the same shipped files of `crates/neural-app/src` and fails on any call outside the guard and its workers that writes the history, the memory or the tab session: the workers' own methods, `TabPersistence::open`, `SessionStore::open`, `tab_session::save`/`clear`/`load` (a load moves a damaged file aside), `HistoryWriter::new`, `MemoryWorker::new`, `HistoryStore::new`/`with_limit`, `MemoryStore::new`, and a `use` that renames one of those writers or imports `save`, `clear`, `load` or `SessionStore` from `tab_session`. A research session is written only through `MemoryStore::save_session` (`ResearchSession::save` is private to `neural-core`), and only the memory worker opens a `MemoryStore`.

Deletions (`remove_file`, `remove_dir_all`) are not writes and stay out of the gate: they are what "Apagar histórico" and the private mode need.

`scripts/test-private-mode.ps1` (CI only: it launches the exe) is phase 0 of the private-mode E2E: it hashes every file under a temporary `NEURALIA_DATA_DIR` before and after a scripted Normal session against a loopback fixture, prints what the session created or changed, and fails on any path that is not in the table above (its allowlist); later briefs extend that allowlist with the Private-mode expectations. Its allowlist is pinned locally by `the_e2e_allowlist_covers_a_normal_guard_session`, which reads the script's rows and its matching rule, drives a `Normal` session through the guard and fails if that session leaves a file without an `Automatic` row, or if a row's path is missing from this table.
